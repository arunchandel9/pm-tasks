MangoEyes Task Hub

Every client request, from any channel, becomes the right task on the right board with the sheet kept in sync, and nobody has to watch the channels to make that happen.

Today
  • Requests arrive on Slack, email, WhatsApp, ad platforms, and in meetings.
  • A PM has to notice each one, work out what is asked, and create the card by hand.
  • The same ask on two channels becomes two cards. Meeting actions get lost.
  • The PM sheet drifts from the board. Nobody can ask "what is open for this client" and trust the answer.
With the hub
  • Everything lands in one intake. Client and team are worked out automatically.
  • Clear requests become a Pulp card, a sheet row, and a reply on the original thread, in under a minute.
  • Unclear ones go to one Slack channel where a person clicks Approve or Edit.
  • When a card moves, the sheet follows. One end-of-day summary. Any PM's own Claude, Codex, or Hermes can ask the hub directly.

The whole picture

Read it left to right. Orange is the automated path. Green, dashed, is the one place a human decides.

One message, start to finish

A client writes in the Slack channel: "The Book Now button on the contact page isn't working on mobile, and can we also get the new price list up this week?"

  1. IntakeThe Slack app sees the message. The channel belongs to Clinic X, so the client is known without any guessing. Stored with a link to the message.
  2. DedupeChecks open requests for Clinic X. Nothing similar in the last 14 days, so it continues. If the same ask had come by email an hour ago, it would attach to that one and reply "already tracked".
  3. ExtractClaude returns two distinct asks: a broken button on mobile, and a price list update. Each with the exact quoted words.
  4. Classify and draftAsk 1: dev issue, Dev team, confidence high. Ask 2: content update, Content team, confidence high. Each gets a drafted title, description, labels.
  5. RouteThe rules table says dev issues go to the Dev board, content updates to the Content board. Priority hint: "this week" mentioned.
  6. ReviewIn phase 1, both drafts appear in #pm-review. A PM clicks Approve on each. Later, high-confidence cases like these skip this step.
  7. CreateTwo Pulp cards, two sheet rows, and one reply in the Slack thread: "Tracked as TASK-131 and TASK-132." The client sees it was heard.
  8. SyncWhen the developer moves TASK-131 to Done in Pulp, the sheet row updates within seconds and it appears in that evening's summary.

After the card exists

The database is the memory of the whole system. Pulp and the sheet are written from it, never the other way round. That is what makes the hub trustworthy.

The hub, from a PM's chair

A PM adds one connection in their own Claude, Codex, or Hermes and can then ask: "What's open for Clinic X and what's blocked?" "Draft a status update for Clinic Y from this week's movement." "Chart tasks created per client this month." Their assistant does the thinking and the visuals. The hub only answers truthfully from the record.

How it works technically

One Next.js app on Vercel. No servers to keep alive. Two Claude calls per message, each with a strict JSON schema, so the output has the same shape every time.

Which steps use AI, and which do not

StepDone byWhat it produces
IntakecodeOne message shape. Client resolved from a config table, never guessed.
DedupecodeExact hash, then similarity against open requests for the same client. Merge, or flag as possible duplicate.
ExtractClaude call 1Summary, list of distinct asks, quoted evidence, deadlines, URLs. Fixed JSON.
Classify + draftClaude call 2Scope, team, request type, priority hint, confidence with reason. Drafted title, description, labels. Fixed JSON.
RoutecodeBoard, list, labels from the routing table.
GatepersonApprove, Edit, Merge, Not a task. Every click is recorded and used to tune thresholds.
Create, sync, summarycodePulp card, sheet row, thread reply, status updates, end-of-day message.

Two AI calls, both with a fixed output shape. That is deliberate: it keeps cost predictable, makes every decision auditable, and lets us score the model against the human clicks.

What never reaches a model

Code filters first, and logs the reason for every skip. Staff messages outside #intake, bot posts, edits, reactions, one-word acknowledgements, exact repeats within 14 days, and short replies inside a thread that already became a task all stop here. Email drops auto-replies and newsletters, keeps ad-platform senders on an allowlist, and strips quoted history so only the new part is read. The result: well over half of raw traffic costs nothing, and what reaches the model is client-authored, non-trivial, and new.

Why these choices

One app, not many agents

The six "agents" in the brief are steps in one pipeline. Separate agents would mean separate things to deploy, watch, and debug, for no gain.

Vercel, not a VPS

Already ours, already on Pro. Webhooks and cron are exactly what it does. No server to patch or restart at 2am.

A pipeline, not Hermes

Hermes is a conversational agent with personal memory. This needs a shared, exact ledger and the same result every time. Hermes stays useful as a client of the hub, with its loop and memory intact.

Claude with strict JSON

Both AI steps return a fixed schema, so outputs can be stored, compared, and scored. Swapping the model later is a two-prompt change.

Postgres is the truth

Pulp and the sheet are views. Dedupe, the audit trail, and "why did it do that" all need one place that remembers everything.

Review everything first

Two weeks of Approve and Edit clicks tell us where the system is reliable. Then the gate opens on evidence, not guesswork.

WhatsApp by forwarding

The WhatsApp Business app has no API. Forwarding costs five seconds and nothing to build. Moving the number to the Cloud API is a later, separate decision.

Pulp sends one webhook

We own Pulp, so "card moved" is one small addition. It replaces polling and makes status sync instant.

Bot where it can live, #intake everywhere else

Automatic intake in channels in our workspace. Sharing a message to #intake is the manual path for a client's own workspace, WhatsApp, or a phone call. Same pipeline, same audit link.

Timeline: 24 working hours, two people

Not a calendar. Twenty-four hours of build with both of us on it, as two long days or three focused sessions. Your admin steps run in parallel with the build; each is 5 to 30 minutes, and each blocks the build if it waits. Milestones are where you can stop and have something real.

What effort cannot compress

  • Google's side of meetings. Reading full transcripts through Google's event system needs a Cloud project, consent screens, and a Workspace admin, which can take an afternoon or a week. So day one uses the simpler path: the Gemini notes doc lands in a Drive folder after every call and the hub reads that folder every few minutes. Full transcripts are a later upgrade if notes are not enough.
  • The review gate. It opens on evidence, not a date: per request type, once 30 approvals have gone through with at least 95% unedited, and never sooner than 3 days. With real volume that is about a week. Meetings always stay reviewed.

Removed so they cannot block: Pulp's card-moved webhook (polled every minute until your developer adds it) and any embeddings service (dedupe is done in the database). Could still add hours: a client channel in the client's own Slack workspace, a Pulp corner that differs from Trello, or Google access held by someone not in the room.
