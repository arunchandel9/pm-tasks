# MangoEyes Task Hub — feature register

The complete list of what the hub does. One line per feature, nothing left implied. The handover guide is built
from this file, and every feature here has a live check in the final round. Add a row whenever a feature is added;
strike a row when one is removed. Decisions that shaped a feature are in `docs/STATE.md`.

Legend: **Live** = deployed and verified on real traffic · **Built** = deployed, unit-tested, live check in the
final round · **Dropped** = decided against, kept here so it is not asked for again.

## 1. Where requests come from (intake)

| 1.6 | Voice notes, short | Audio forwarded to the DM (WhatsApp notes included, with or without a file extension) goes to Google Speech-to-Text v2 with the Chirp model (needs the "Cloud Speech Client" role on the service account), which decodes the file itself and handles accents; falls back to v2 "long", then to the v1 engine. Both engines get a vocabulary hint list: every client name and alias plus agency words (CTA, homepage, hero image…). The client is set only when the transcript contains a client name or alias as a whole word (or the thread / a name typed just before says it). A near-miss ("a bella" ~ Abela) is a suggestion only: the DM asks "I heard 'a bella', is it Abela? Reply yes, or the client name" and nothing is filed until the person answers; by mail the suggestion appears on the "which client?" card. No name at all → the same question with no suggestion (rule since 2026-09-14: a client is confirmed only with full clarity). The understanding step is told it is a transcript, keeps to one ask unless clearly two, and never invents detail. The thread gets "🎙️ Voice note received, transcribing…" within seconds, and that same message is edited into "Heard: …" when the transcript is ready, so a mishearing is visible and a one-line reply corrects the card (2026-09-15). Diagnostics: `voice_last` on health and hub_status. | Live (A5, A6: short notes from DM and Drop, a 163 s note, "which client?" and "noted, no card" replies) |
| 1.7 | Voice notes, long (up to 20 min) | Long audio goes to a Cloud Storage bucket and a long-running transcription; the hub polls until the text is ready, then processes it. Longest verified: 163 seconds; the bucket path waits for the first real long note. | Built |

Forwarded mails are unwrapped; signatures, "Sent from …" lines, Google Groups footers and quoted earlier emails (Gmail "On … wrote", Outlook From/Sent/To/Subject blocks, ">" lines) are separated from what the sender wrote: the ask is taken only from the sender's own words, and the earlier thread is handed to the model as labelled context ("Earlier in this thread, context only", capped at 1,500 characters) so a short reply like "too little too late" is understood against what it answers (2026-09-15); each mail processed once (Message-ID dedupe), then labelled "Task Hub". Mail Arun sends from arun@ to intake@ counts too: intake@ is an alias of arun@, so such a mail is one Gmail message in both Sent and Inbox (fixed 2026-09-14; Sent was excluded before). Drafts are never read (the phone's share sheet writes a draft seconds before sending; fixed 2026-09-14). Staff mail is dropped as "outgoing" only when it is neither a forward nor addressed To intake@ (a staff mail that only copies intake@ while replying to a client is outgoing). Audio attachments are transcribed like DM voice notes, short and long, so the phone path is WhatsApp → Share → Gmail → intake@ (the phone share sheet cannot target an app DM). | Live (one forwarded mail verified; audio built 2026-09-12) |
| 1.9 | Google Meet notes | One headline per meeting in the feed, named after the call ("📝 Introduction Call · Leicester MediSpa · 15 Sep"; a generic "Meeting started …" title reads "Meeting"), everything else in its thread in reading order (2026-09-22): the tally and notes link (rewritten as the action jobs finish), **In short** (three to five lines), **Decided** (one line per decision; a decision about work that already has a card is written on that card as a comment and linked from the line), **To do** (the team's action items, one proposal card each, 3.1: nothing reaches Pulp without a tap, internal meetings included), **Also raised** (ideas, which go to Monday's list, 4.8; the client's own to-dos, no card). Each organiser shares their Meet folder ("Meet Recordings" or "Google Meet") with the service account once. Every 5 min the hub finds every "… Notes by Gemini" doc it can see, at most two per run in their own budget, with a trace before every slow step; a doc Gemini has not finished (placeholder text, under 400 characters, "no usable content") is left and read again every 30 min for up to 6 hours; a doc that fails three attempts is set aside and reported. Action items run as queue jobs of five per client. Meetings are read from the moment the hub first looked, never the backlog. `/api/meet-check` lists who is covered; `?run=1`, `?reread=<doc>`, `?since=now`, `?forget_cards=<doc>`. | Live (five meetings read 15–17 Sep); thread layout Built 2026-09-22 |
| 1.10 | MCP `add_request` | A PM's Claude or Codex files a request straight into the hub; it lands in Staging like any other. Claude accounts are shared, so the connector never tells Claude who the owner is, and the tool requires both the name the person gave and a flag that Claude asked for it in the chat (tightened 2026-09-15 after Claude filled in the owner's name unasked); feed and sheet read "Anuj via Claude-Arun": the person, then the Claude account it came through (wording set by Arun 2026-09-15). One key per Claude account, named after it. The only write action exposed; approving, moving or closing cards from an assistant is not possible by design (2026-09-14). | Live (A12) |
| 1.11 | Unknown client | If no client can be matched: from the DM, the hub asks in that thread and continues when the person replies with the name; from Slack, email or a meeting, a "which client?" card goes to the feed for anyone to answer. Picking or typing the client runs the message at once, so the card and feed line follow within seconds, not on the next minute (2026-09-15). In the DM, "yes" accepts the hub's suggested client (voice notes), any client name overrides it. Either way the message is stored with reason `unknown_client` and listed under "Needs a person" in the summary until resolved. The feed carries finals only. | Live |
| 1.12 | Kill switch | `INTAKE_PAUSED=true` in Vercel, then a redeploy: messages are still stored but nothing is created, posted or written; each is retried every 5 minutes and goes through once the switch is off. Not soak-tested, by decision on 15 Sep: tried only if ever needed. | Built |
| 1.13 | "Task Hub Drop" space (phone share) | The phone's share sheet lists spaces reliably but shows the app's DM only while it is fresh in the phone's cache (confirmed 2026-09-14). So the team shares text and voice notes into the space **Task Hub Drop**, no mention needed. Google does not push unmentioned space messages to an app, so the hub reads the space itself every 20 seconds as Arun (domain-wide delegation, scope `chat.messages.readonly`, same service account as the mailbox; `/api/inbox-tick`) and hands each new message to the same handler as a DM: same client rules, same voice path, same question in the message's thread, same feed lines. The space is found by name among the spaces the app is a member of (`GCHAT_INBOX_NAME`, default "Task Hub Drop"); only messages after the hub first looked are read; a mention in that space is ignored so nothing runs twice. Diagnostics: `chat_inbox_last` on health and hub_status. | Live (phone tests passed 2026-09-14) |

## 2. Understanding the request

| # | Feature | How it works | Status |
|---|---|---|---|
| 2.1 | Noise filter | Acknowledgements, emojis, attachment-only posts, tiny thread replies and known bot senders never reach a model. In the DM, "ok thanks" or a 👍 gets no reply at all; it is stored as skipped. | Live |
| 2.2 | Extract: five kinds | One model call splits a message into distinct items and gives each exactly one kind (Arun, 2026-09-22): **task** (a MangoEyes person must produce something: a page change, content, a design, an ad, an automation, a video, a report), **reminder** ("remind me tomorrow", "chase on Friday", only from a team member), **idea** (a suggestion, not agreed), **rule** (a standing instruction on how to work with this client) or **note** (information, scheduling, access and logins, a link or material, the client's own to-do, conversation). Edits to the same page are one task, never several. A stated problem ("… is not working") is a task by rule. Each item also says whether the sender called it urgent, any timing, and a team member named to do it. Only tasks go on to classification; the other four never become cards. Before this, every instruction became a card: 80 Staging cards in the week of 15 Sep, about half of them scheduling, access, feedback and conversation. | Built 2026-09-22 |
| 2.3 | Classify | Each ask gets a request type, department, priority with reason, and a card title and description. Prompt caching keeps cost low; every call is logged with tokens and cost. Output budgets: extract 4,000 tokens, classify 1,500, meeting 3,000; an answer that still gets cut off is retried once with four times the room (fixed 2026-09-15 after a 14-item meeting arrived as cut-off JSON and stalled). | Live |
| 2.4 | Deterministic routing | `config/routing.yaml` decides board, list, labels, SLA due date and P1 keywords. The model never decides these. | Live |
| 2.5 | Urgent means P1 | "site down", "form not working", "ad disapproved", "hacked" and the rest force P1 with a 4-hour due time; so does the sender saying it is urgent in plain words ("most urgent", "asap", "today", "within 24 hours"; 2026-09-22, after "the MOST URGENT task" was proposed at P2). A timing the sender gives ("by Friday", "within 24 hours") becomes the due date; otherwise the priority's default (P1 4 hours, P2 3 working days, P3 5). Both show on the proposal card, where they can be changed before the card exists. | Built 2026-09-22 |
| 2.6 | Dedupe and follow-ups | A message that matches an open task (same thread, or similar text within the window) is noted as a comment on that card instead of creating a new one. A message never matches its own earlier cards, so a re-run finishes what a cut-off run started instead of filing everything as a repeat (fixed 2026-09-15). The feed shows a 🔁 line with the card link, for exact repeats from the DM or Drop space too (added 2026-09-14: the feed is the record, the sender's thread is not enough). | Live |
| 2.7 | Meeting sorter | Each notes doc is split into actions, ideas, decisions and discussion, and every action is marked by whose side does it: the sorter is given the team by name (the members of the Task Hub Drop space plus agency addresses in the call), so anyone else named in the notes is the client's side. Only the agency's actions become cards (under that client; MangoEyes-internal items stay internal). The client's own homework (sign, grant access, send photos, confirm dates) makes no card: it is listed in the meeting's thread under "With the client" and counted in the headline ("5 with the client"), so the team can chase it without cards for work that is not theirs (rule from Arun 2026-09-15 after an introduction call produced cards for the client's to-dos). Ideas and decisions are stored and searchable. | Live |
| 2.8 | Daily model cap | A per-client daily cap on model calls stops a runaway thread from spending money. | Built (never reached) |
| 2.10 | Not a task, never silent | A note (information, scheduling, access, a link, the client's to-do) makes no card and gets one ℹ️ "noted, no task" line with the items and the words in its thread; a reminder gets "⏰ reminder set for Heena", an idea "💡 idea noted for Monday", a rule "📌 rule noted". The sender's DM thread says what happened ("reminder set; it comes back to you in the feed at that time"). | Built 2026-09-22 (was 2.10 "Understood, no card", Live since A6) |
| 2.9 | Unhappy client, no ask | When a client's message has no ask but reads as displeased ("Too little too late"), the hub makes no card and posts one ⚠️ line in the feed: client, the words, the source link, "a person should reply". The message is listed in the brief under "Waiting on you" until handled. Added 2026-09-15 after a forwarded client reply was misread as a task. | Live (A8) |

## 3. Cards, approval and the sheet

| # | Feature | How it works | Status |
|---|---|---|---|
| 3.1 | The proposal card | A task is never made on its own. The hub posts a card in the message's feed thread, addressed to the person by @mention ("Heena: this needs your decision"), with the task title, the words, and four dropdowns, all visible and pre-filled: **Department** (the hub's guess), **Assign to** (everyone on the department boards; pre-selected when the message named someone), **Priority** (P1 when urgent) and **Due** (the hub's date first). Three buttons: **Create card**, **Remind me instead**, **No card**. The card is replaced by the outcome line ("✅ Card created by Heena · Content · P1 · due Tue 23 Sept 16:00 · assigned to Anuj · open the card"). Typed replies in the thread do the same: "create", "create for Anuj", "remind me Friday", "no card". A proposal nobody answers is listed in the brief under Waiting on you until it is. The client's rules are printed on the card. Decision 2026-09-22: replaces the Staging list (3.3). | Built 2026-09-22 |
| 3.2 | Needs scope card | New page and new feature asks went to a separate **Needs scope** list. Dropped 2026-09-15 by Arun: one list for everything; the "new-page" / "feature" label on the card marks what needs scoping. | Dropped |
| 3.3 | Create card → To Do, assigned | **Create card** makes the Pulp card straight in the department's To Do (the client's override list if set), with the assignee, priority, due date, the labels `Task Hub`, client and priority, the description, the original words, the source link and the client's rules, and writes the sheet row at the same moment. No Staging, no drag, no second step. **Remind me instead** makes no card: a reminder for the person who tapped, two days out by default (reply a day in the thread to move it). **No card** records the decision and makes nothing. Cards made before 22 Sep still sit in Staging: dragging them out still counts as approval (3.3a, 3.3b, 3.5 keep working for them). | Built 2026-09-22 (drag = approval Live since B2 for older cards) |
| 3.3a | PMs board: rows by hand | A card on the **PMs board** gets no sheet row from the hub (`sheet: manual` in `config/boards.yaml`, decision 2026-09-18). Dragging it out of Staging within the PMs board is still the approval; the PM adds the row by hand when wanted (paste the card link in the client's tab, the Task cell may stay blank) and the mirror adopts it within 10 minutes, after which Status follows the card as for any hub card. Moving the card from the PMs board to any list on a department board writes the row at that moment. | Built 2026-09-18 |
| 3.3b | Cross-board moves | When a hub card changes board, the hub records the new board and re-derives the department from `config/boards.yaml` (the sheet's Department cell, the card link and the target list follow it) and puts the `Task Hub` and client labels back, since Pulp labels belong to a board. A card that already has a row keeps it; rows are found by card id, so the board part of the link may change. | Built 2026-09-18 |
| 3.4 | Sheet row with stamp | The row lands in the client's tab with title, department, priority, assignee, Pulp link, source link, created and due dates. The Comments cell reads "Task assigned. Added by Task Hub · approved by drag in Pulp · 9 Sep 2026, 14:30 IST · from Slack, Dr Mehta". | Live |
| 3.4a | Yellow new rows | Every row the hub adds is coloured light yellow (`new_row_colour` in `config/sheet.yaml`). A person checks it is in the right place, moves it up or down if not, and makes it white. Moving a row never breaks the hub: rows are found by their Pulp link, not their position. | Live (B4) |
| 3.5 | Status sync | Every hub card is checked by id: Staging cards every minute (the drag is the approval), cards already out of Staging every 2 minutes, ten fetched in parallel (2026-09-18: one after another kept the minute function alive most of the minute, and Vercel bills every second of that). Status in the sheet follows the card's list; Done fills Date Completed and moves the row below the DONE divider; moving back out of Done reopens it. | Live |
| 3.6 | Hand-made cards | A card someone creates directly in Pulp and links in the sheet by hand is picked up by the sheet mirror (every 10 min), even when the Task cell is still blank: the hub then fills the Task cell from the card's title. From then on the hub checks it every 2 minutes (ten fetched in parallel; was 40 a minute one after another until 2026-09-18) and writes Status only when the card moves list (Done also closes the row). First look never overwrites a typed status. | Live |
| 3.7 | Sheet mirror | Every 10 min all client tabs are read into the hub (history from before the hub and hand-typed rows), so Claude answers from the PMs' own record. A row that leaves the tab (deleted, or re-keyed by an edit to its serial or title) leaves the hub on the next run, so no ghosts and no task listed twice (fixed 2026-09-15: one TED task appeared seven times). A tab that reads back empty is left alone. Never writes to the sheet. | Live (1,164 rows) |
| 3.8 | Retry without re-approving | A card that failed to create is retried by a background job that never changes the approval; a failed sheet write is retried the same way. | Built (never needed in the soak; queue empty throughout) |
| 3.9 | Client board overrides | A client's Config row can point any department to another board or list; blank means the default in `config/boards.yaml`. Decision 2026-09-15 (Arun): every card goes to the department boards, no client or internal board; the override stays available, unused and untested, for the day it is wanted. | Built, not in use |
| 3.10 | New-page chain | Seven linked sub-cards per new page. | Dropped 2026-09-10: pages are mostly one person's work; the PM adds cards by hand |

## 4. Keeping a person in the loop

| # | Feature | How it works | Status |

Every line the hub writes says who it is for and what to do, in the team's words, with the action on the button in full (Arun, 2026-09-22: nothing that only makes sense once you know the system). The hub knows the space by ID, so renaming it changes nothing. | Live (C1, from block A); wording pass 2026-09-22 |

| 4.3 | Receipt rule | The feed line is the receipt. If no line appears within 2 minutes, send the message again. | Live |
| 4.4 | DM replies only when needed | The DM answers in the thread only when the sender must act ("Which client is this for?", "I can read text and voice notes, not images"), when nothing was created ("Nothing created: …", "reminder set; it comes back to you in the feed at that time"), or when a short or uncertain ask was proposed ("To confirm in the feed thread (one tap): … Reply here to correct or add anything"). A reply in that thread becomes a comment on the card. Otherwise the feed line is the receipt and the DM stays quiet. | Live (C2, from block A) |
| 4.5 | Reply reminders | A client message in Slack that no MangoEyes person has answered gets a reminder in the feed after 20 minutes, again at 1 hour, again at 1 day, then every day until handled, weekends included (decision 2026-09-18: an urgent client problem must still reach someone; the 🔴 day-old lines are Monday's list). One line each ("💬 *Abela* · no reply for 20 min · Slack"; ⏰ at an hour, 🔴 at a day); the thread holds the sender, the words, whoever the client tagged, the Slack link, "PMs: reply to them in Slack and these reminders stop. Never for a thank-you, an "ok noted" or a message the model reads as closing the exchange (`needs_reply`), never for repeats or filtered noise. One reminder per channel per mark, however many messages. The brief lists clients still waiting under Waiting on you. Marks in `config/noise.yaml`. Rebuilt 2026-09-15. | Built (proves itself on the first real client message) |
| 4.6 | Daily brief: Today | 10:00 India, Monday to Friday (Vercel Cron 04:30 UTC). A line appears only when a named person has to do something about it today; nothing else (Arun, 2026-09-22: the old 23:00 brief was a log of nine sections nobody read). Headline: "📋 Today · Tue 23 Sep · 3 things waiting on Heena, 1 on the PMs · 2 overdue". Thread: **Waiting on you**, one line per item, each @mentioning its person (proposals not answered, reminders due, clients waiting in Slack, "which client?" unanswered, unhappy clients); **Overdue** (hub cards with a due date the hub set, P1 first, with the assignee, never the sheet's history); **Issues (Arun)** when a reader stopped or a message failed; **Yesterday** in one line of counts. Nothing is cut to "and N more". **Nothing waiting: no post at all.** `/api/eod?dry=1` previews it. | Built 2026-09-22 (the 23:00 brief was Live from 15 Sep) |
| 4.7 | Reminders | A team member's "remind me tomorrow", "chase the GP on Friday", or **Remind me instead** on a proposal makes a reminder for that person: at its time (10:00 India when only a day is given; two mornings out when nothing is said) one line in the feed @mentioning them ("⏰ @Heena: reminder you asked for · *The Eye Doctor* · chase the GP for a date · press Done when handled") with a **Done** button in its thread; not pressed, the same line again every morning until Done. A day typed in the thread ("Friday", "next week", "tomorrow 4pm") moves it; "done" closes it. A client never gets a reminder set (their waiting is 4.5). Timing words understood: today, tomorrow, day after, in N days / working days / weeks, weekday names, next week, end of month, dates, "within 24 hours", "at 4pm". Decision 2026-09-22 (before, "remind me tomorrow" became a card on the PMs board). | Built 2026-09-22 |
| 4.8 | Ideas on Monday | Every idea (from any channel or a meeting) waits for a decision, not for memory. Monday 10:00 India, one line to the PMs ("💡 PMs: 4 ideas from last week. Decide which become tasks. · House Of Health 2 · The SKIN Firm 1 · Abela 1") and in its thread one card per idea, in full, with the client, who said it, where and when, and two buttons: **Make it a task** (the normal proposal card follows in the same thread) or **Not now**. An idea nobody decides on comes back the next Monday marked "still waiting for a decision since 15 Sep", until someone decides. `/api/eod?ideas=1` forces the post on any day. | Built 2026-09-22 |
| 4.9 | Client rules | "Next time ask my permission before changing appointment durations" is stored as a standing rule for that client (📌 line in the feed) and printed at the bottom of every proposal card and every Pulp card the hub makes for that client from then on, so the person doing the work sees it without asking. Nothing else; kept minimal by decision 2026-09-22. | Built 2026-09-22 |

## 6. Nothing gets lost (reliability)

| # | Feature | How it works | Status |
|---|---|---|---|
| 6.1 | Every message stored first | The raw message is saved before anything else happens, with a reason code if skipped. | Live |
| 6.2 | Retry queue | Card creation, comments, sheet writes, transcription polls and message processing all go through a queue with backoff. Abandoned jobs are reported. | Live |
| 6.3 | Watchdog | Every 10 min: half-processed messages are reprocessed, tasks without a card get one (without re-approving), stuck jobs are listed under "Needs attention" in the summary. any cost or summary document are written from this file, never from memory.
